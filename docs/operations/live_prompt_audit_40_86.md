## A. 조용한 오답 — 최우선

막힌 요청보다 나쁘다. 사용자는 SQL 을 받았고, 그 SQL 은 그럴듯하며, 틀렸다.

### A1. `Or` 가 `Filter` 최상위일 때 괄호가 없다 → 상관 술어가 OR 밖으로 샌다

**#55 `사료, 간식, 장난감 중 하나라도 구매한 회원을 추출해줘.`** 가 출고한 SQL:

```sql
EXISTS (SELECT 1 FROM CRM_SL_ORDERDETAILMALL OD LEFT JOIN CRM_CM_PRODUCT OD_PRODUCT ON ...
        WHERE OD.MEMBER_NO = B.MEMBER_NO AND ((…사료…)) OR ((…간식…)) OR ((…장난감…)))
```

`AND` 가 `OR` 보다 강하게 묶이므로 이 술어의 뜻은 `(상관 AND 사료) OR 간식 OR 장난감` 이다.
둘째·셋째 항에는 `B.MEMBER_NO` 가 없다 — **주문 상세에 간식이나 장난감이 한 줄이라도 있으면
모든 회원에 대해 EXISTS 가 참**이 된다.

실DB 실측(CRMDW):

| | 회원 수 |
|---|---|
| 출고된 SQL | **69,308** |
| 괄호를 씌운 SQL | 8,395 |
| 정상 상태 전체 회원 | **69,308** |

세그먼트가 전체 회원과 **정확히 같다**. 캠페인 발송 대상으로 그대로 나갔다면 전수 발송이다.

**원인.** [event_compiler.py:1291](../../event_compiler.py#L1291) `_combine` 은 피연산자마다 괄호를
씌우지만 **합성 결과 자체는 감싸지 않는다**:

```python
return CompiledCondition(sql=joiner.join(f"({item.sql})" for item in compiled), params=params)
```

그 문자열이 [event_compiler.py:795](../../event_compiler.py#L795) 에서 `plan.where` 리스트에 그대로
들어가고, [event_compiler.py:1051](../../event_compiler.py#L1051) 이 그 리스트를 `" AND ".join(...)` 으로
잇는다. `Or` 가 `And` 안에 중첩돼 있으면 바깥 `And` 가 괄호를 씌워 주므로 드러나지 않는다 —
**최상위가 `Or` 인 `Filter` 에서만** 샌다. 결정론 재현:

```python
# Filter(source, Or(...)) — 샌다
EXISTS (... WHERE EO.MEMBER_NO = B.MEMBER_NO AND (EO.PAYMENT_AMT >= 100000) OR (EO.PAYMENT_AMT < 1000))
# Filter(source, And(TimeFilter, Or(...))) — 정상
EXISTS (... WHERE EO.MEMBER_NO = B.MEMBER_NO AND (…) AND ((…) OR (…)))
```

**범용 해결책.** 문자열을 조립하는 계층에 **결합도(precedence)** 개념을 넣는다. 지금은
`CompiledCondition` 이 "SQL 조각"만 들고 있어서, 그 조각을 받는 쪽이 감쌀지 말지를 판단할 근거가 없다.

1. `CompiledCondition` 에 `is_disjunction`(또는 `precedence`) 필드를 추가한다.
2. `AND` 문맥에 조각을 삽입하는 **모든** 자리(`Filter` 분기, `plan.where` 확장)는 그 필드가 참이면
   괄호를 씌운다. 자리마다 판단하지 않고 삽입 헬퍼 하나로 모은다.
3. 최소 수정만 원한다면 `_combine` 에서 `joiner` 가 `" OR "` 일 때 결과 전체를 괄호로 감싼다.
   비용은 잉여 괄호뿐이고, 잉여 괄호는 뜻을 바꾸지 않는다.

**가드(이 결함이 다시 못 들어오게).** 개별 사례 테스트로는 부족하다 — 새 컴파일 경로가 생기면
같은 함정을 다시 판다. 불변식으로 고정한다:

> 컴파일된 조건 문자열은, `AND` 로 이어붙였을 때 뜻이 변하지 않아야 한다.
> 즉 **최상위(괄호 깊이 0)에 `OR` 이 남은 조각을 반환하지 않는다.**

property 테스트로 임의 `And`/`Or`/`Not` 트리를 만들어 위 성질을 검사하고, 동시에 출고 SQL 전체에
대해 "같은 괄호 깊이에 `AND` 와 `OR` 이 함께 있는가"를 검사하는 린트를 러너에 넣는다(이번 감사에서
25건 중 #55 하나만 걸렸다 — 검사 자체는 몇 줄이다).

### A2. 주문 단위 임계가 회원 단위 합계로 접힌다

**#42** `최근 90일 동안 총 구매금액이 30만원 이상인 회원` 과
**#43** `최근 90일 동안 구매금액이 30만원 이상인 주문을 한 회원` 이 **바이트 동일한 SQL** 을 냈다
(둘 다 `SUM(EO.PAYMENT_AMT) >= 300000`, segment_label 도 `구매 sum >= 300000` 로 같다).

#43 은 "그런 **주문**이 있는 회원"이므로 `EXISTS(주문 중 PAYMENT_AMT >= 300000)` 이다. 실DB 실측
(적재 전 구간 기준, 90일 창은 적재 밖이라 0건이므로 창을 넓혀 두 해석의 크기만 비교):

| 해석 | 회원 수 |
|---|---|
| 합계 ≥ 30만 (출고된 것) | 9,585 |
| 단일 주문 ≥ 30만 (요청한 것) | **688** |

14배 차이다. 같은 문장 형태가 #40(`2019년에 이십만원 이상을 구매한 고객`)에서도 합계로 접혔는데,
그쪽은 원문이 애매해 합계 해석이 방어 가능하다. #43 은 `…인 주문을 한` 이라고 **명시**했다.

**범용 해결책.** 임계값에는 값·단위뿐 아니라 **적용 grain** 이 따라다녀야 한다.
카탈로그의 metric 선언에는 이미 `grain` 이 있다(`purchase_amount.grain = "subject"`). 없는 것은
원문에서 grain 을 읽어 **행 단위 비교**로 낮추는 경로다.

1. 요구 표현에 `grain: subject | row` 를 필수로 싣는다(기본값을 두지 않는다 — 기본값이 곧 추측이다).
2. `row` 이면 `Exists(Filter(Source, Comparison(field, op, literal)))` 로,
   `subject` 이면 지금처럼 집계 비교로 낮춘다. 둘 다 기존 IR 로 표현된다 — 새 노드가 필요 없다.
3. grain 을 확정할 수 없으면 되묻는다. `#40` 처럼 원문이 실제로 애매한 자리가 여기다.

**가드.** `#42` 와 `#43` 이 **서로 다른 SQL** 을 내야 한다는 회귀 테스트. 지금은 바이트 동일이므로
이 테스트 하나가 곧 현재 상태를 실패로 만든다.

### A3. 부재를 최종값 부등호로 근사한다

**#68 `앱으로 로그인하지 않은 회원`** → `B.LAST_LOGIN_CHANNEL != 'DEVICE_TYPE_CD.APP'`.

두 가지가 어긋난다.

- **뜻**: 요청은 "앱으로 로그인한 적이 없다"(부재)인데, SQL 은 "**마지막** 로그인이 앱이 아니다"다.
  어제 앱으로 로그인하고 오늘 PC 로 로그인한 회원이 대상에 들어온다.
- **NULL**: 로그인 이력이 없어 `LAST_LOGIN_CHANNEL` 이 NULL 인 회원은 `!=` 가 UNKNOWN 이라 **빠진다**.
  "앱으로 로그인한 적 없음"에 가장 확실히 해당하는 회원이 제외된다.

**범용 해결책.** 이 저장소에는 이미 판정 근거가 선언돼 있다 —
`temporal_bindings.json` 의 `observation_capabilities.supports_all_occurrences` 가
"구간 안 임의 발생의 존재를 판정할 수 있는가"이고, 최종값만 아는 표현(`latest_only`)은 이 값이 거짓이다.

1. **부재(never) 의미는 `supports_all_occurrences=true` 인 관측에만 사상한다.** 최종값 스냅샷
   바인딩에 부재를 사상하지 않는다 — 그 표현은 그 질문에 답할 수 없다.
2. 답할 수 없으면 정직한 미지원으로 닫고, 개방 조건("채널별 로그인 이력 소스가 필요")을 적는다.
3. 최종값 비교로 답할 수 있는 문장("**최근** 로그인 채널이 앱이 아닌")과는 머리(head)로 가른다.
4. 부정 비교에는 NULL 정책을 명시한다(`!= 'X'` 가 아니라 `(col IS NULL OR col != 'X')`).
   `NullPolicy` 어휘가 이미 있으므로 값을 고르는 문제이지 새 개념이 아니다.

## B. 거짓 미지원 — 컴파일되는데 "못 한다"고 답한다

세 항목은 **컴파일러를 직접 호출해 SQL 이 나오는 것을 확인**했다. 즉 능력 부재가 아니라 방출·판정 결함이고,
사용자가 받은 문구는 사실이 아니다.

### B1. 창을 가진 부재 (#66, #62)

| id | 원문 | 사용자가 받은 문구 |
|---|---|---|
| 66 | 최근 90일 동안 주문하지 않은 회원을 추출해줘. | 요청한 조건을 현재 실행 자산으로 표현할 수 없습니다. |
| 62 | 최근 30일에는 구매하지 않았지만 과거 구매 이력은 있는 회원을 찾아줘. | 기간 값이 없습니다. |

결정론 컴파일 결과(실제 실행):

```sql
-- #66
NOT EXISTS (SELECT 1 FROM CRM_SL_ORDERHEADERMALL EO
            WHERE EO.MEMBER_NO = B.MEMBER_NO
              AND EO.ORDER_DATE >= CONVERT(CHAR(8), DATEADD(DAY, -90, GETDATE()), 112))

-- #62
(NOT EXISTS (… AND EO.ORDER_DATE >= CONVERT(CHAR(8), DATEADD(DAY, -30, GETDATE()), 112)))
AND (EXISTS (SELECT 1 FROM CRM_SL_ORDERHEADERMALL EO WHERE EO.MEMBER_NO = B.MEMBER_NO))
```

정확하다. 창 없는 부재(#67 `장바구니에는 상품이 있지만 한 번도 구매하지 않은`)는 SQL 이 나오는데
**부정 절에 창이 붙는 순간** 막힌다. 코퍼스의 #2(`최근 3개월 내 주문한 적은 있지만 최근 30일간 구매가 없는`,
기대 `sql`)도 기준선에서 `unsupported` 다 — 같은 군집이며 이 결함은 이미 세 항목을 먹고 있다.

### B2. 사건 로그에 대한 칸별 전칭 (#51)

`최근 3개월 동안 매월 한 번 이상 구매한 회원` → `unsupported`. 결정론 컴파일:

```sql
(EXISTS (… ORDER_DATE >= '20260701' AND < '20260801'))
AND (EXISTS (… ORDER_DATE >= '20260601' AND < '20260701'))
AND (EXISTS (… ORDER_DATE >= '20260501' AND < '20260601'))
```

막는 것은 컴파일러가 아니라 시간 연산자 선언이다.
[temporal_ir/operators.py:796](../../temporal_ir/operators.py#L796) 의 `EVERY_BUCKET` 은
`accepted_representations` 에 `PERIODIC_SNAPSHOT` 과 `VALIDITY_INTERVAL` 만 두고 `EVENT_LOG` 를 뺐으며,
`required_capabilities` 로 `supports_complete_bucket_enumeration` 을 요구하는데 구매 이벤트 바인딩은
그 값이 거짓이다.

그 선언은 **상태**에 대해서는 옳다(사건 로그는 "그 달에 이 값이었다"를 답하지 못한다).
그러나 #51 이 묻는 것은 상태가 아니라 **발생**이고, 사건 로그는 발생을 전부 보관한다
(`supports_all_occurrences = true`). 즉 하나의 연산자가 두 질문을 겸하고 있어서 답할 수 있는 쪽까지 막혔다.

### B1·B2 공통 범용 해결책

**지원 여부는 이름으로 판정하지 않고 낮춰 봐서 판정한다** — 이 저장소가 이미 선언한 원칙이다
([lowering_planner.py](../../lowering_planner.py) 모듈 문서). 지금 그 원칙이 적용되는 범위는 의무 두 종류
(`aggregate_comparison`, `member_state_history`)뿐이고, 나머지 요구는 여전히 라벨과 선언표로 판정된다.

1. **미지원 문구를 내기 전에 컴파일을 시도한다.** 종류를 하나씩 늘리는 대신, 종류에 무관한
   "후보 canonical 표현을 만들어 컴파일해 본다" 경로를 미지원 판정 앞에 둔다. 성공하면 그 계획을 쓴다.
   실패하면 그때 나온 컴파일러의 사유가 곧 사용자 문구가 된다(지금의 뭉뚱그린 문장보다 정확하다).
2. **부정 절의 시간 소유권을 인정한다.** 창이 부정 절에 붙었을 때 문장 전체의 기간 결핍으로 올리지
   않는다(케이스 E 와 같은 수리).
3. **칸별 전칭을 두 연산자로 가른다.** 상태용 `EVERY_BUCKET`(지금 것)과 발생용 칸별 존재를 나누고,
   후자는 `AND(칸별 Exists)` 전개로 낮춘다. 이때 필요한 능력은
   `supports_complete_bucket_enumeration` 이 아니라 `supports_all_occurrences` 다.
   판정 근거가 선언에 있으므로 코드가 아니라 연산자 정의 한 항목이 는다.

**가드.** "컴파일되는데 미지원으로 답하지 않는다"를 직접 고정한다 — 미지원으로 닫힌 요구에 대해
컴파일 시도가 성공하면 실패하는 테스트. 항목별 기대값이 아니라 **모순 금지** 불변식이다.

## D. 시간 축의 표현 한계

### D1. 시각(시:분:초) 해상도 — 6건

| id | 원문 | 귀결 | 실제로 일어난 일 |
|---|---|---|---|
| 69 | 2026년 7월 1일 23시 59분 59초까지 주문한 회원 | clarification | SQL 은 만들어졌고 **시각만 사라졌다**(`19000101~20260701`). 의미 검증기가 잡았다 |
| 79 | 2026년 7월 1일 23시 59분 30초 이후 주문한 회원 | clarification | 〃 (`20260701~99991230`) |
| 80 | 7월 1일 오전 9시 ~ 7월 2일 오후 6시 30분 | clarification | 〃 (`20260701~20260702`) |
| 70 | 밤 11시부터 다음 날 새벽 2시 사이 | unsupported | 날짜가 없어 창 자체가 서지 않는다 |
| 81 | 오전 9시부터 오후 6시 사이 | unsupported | 〃 |
| 82 | 최근 24시간 동안 주문한 회원 | clarification | `시간`이 창 단위가 아니라 맨 '최근'으로 취급돼 기간을 되물음 |

**의미 검증기는 제 역할을 했다.** #69 의 문구는 정확하다 —
`시각 조건(2026년 7월 1일 23시 59분 59초까지)이 SQL 에 반영되지 않음(날짜만 걸면 조건이 넓어짐)`.
날짜만 걸린 SQL 이 그대로 나갔다면 조용한 오답이었을 것이다(케이스 A 와 같은 부류).

**원인은 하나다: 창의 단위에 하루보다 잘은 것이 없다.**
[event_ir.py:100](../../event_ir.py#L100) `WINDOW_UNITS = ("day", "week", "month", "year")` 이고,
시간 바인딩은 `semantic_grain: day` 이며, 칸보다 잘게 나눈 구간은
[temporal_ir/lowering.py:296](../../temporal_ir/lowering.py#L296) 의
`temporal_window_not_bucket_aligned` 가 막는다. 그 차단은 옳다 — 칸보다 잘은 구간을 칸으로 접으면
요청하지 않은 대상이 나온다.

**그런데 시각 자체는 이미 표현된다.** `purchase.order_time`(`ORDER_TIME`) 필드가 카탈로그에 있고,
평범한 `Comparison` 으로 컴파일된다(결정론 확인):

```sql
EXISTS (… WHERE EO.MEMBER_NO = B.MEMBER_NO AND (EO.ORDER_TIME >= '090000') AND (EO.ORDER_TIME <= '180000'))
```

**범용 해결책. 시각을 창(window)이 아니라 술어(predicate)로 분리한다.**

1. 창은 **날짜 칸**으로 유지한다(정렬·적재 판정·인덱스가 전부 날짜 기준이다).
2. 시각 조건은 같은 소스의 `ORDER_TIME` 비교로 따로 낮춘다. 두 조각이 한 `Filter` 안에서 `And` 로 만난다.
3. **경계일에만 시각을 건다.** 여러 날에 걸친 범위(#80)에서 양 끝에 시각을 걸면 가운데 날이 잘린다
   — 7월 1일 18:30 이후 주문이 사라진다. `calendar_window` 에 이미
   `from_time` · `open_end` 문법이 있으므로(코퍼스 #79 노트) 없는 것은 구조화기가 그 슬롯을 채우는 일이다.
4. **자정을 넘는 시각대는 `OR`, 넘지 않으면 `AND`** 다(#70 vs #81). 두 항목이 같은 두 경계로 정반대
   집합을 만들므로 함께 고정해야 뒤집기 실수가 드러난다.
   ⚠️ **A1 을 먼저 고쳐야 한다.** 지금 상태에서 `Or` 술어를 내면 그 순간 상관 술어가 새서
   전체 회원이 나온다 — 시각 축을 여는 것이 곧 새로운 조용한 오답이 된다.
5. `시간`(hour)을 롤링 창 단위로 열지 말지는 별개 결정이다(#82). 열지 않기로 하면
   "시각 해상도 롤링 창은 미지원"이라고 정직하게 답해야지, 맨 '최근'으로 되묻어서는 안 된다 —
   사용자는 기간을 **말했다**.

### D2. 창의 방향과 두 경계 (#85, #86)

- **#86 `향후 7일 안에 구매예정일이 도래하는 회원`** — 표면 계층은 미래 방향을 **안다**
  ([calendar_window.py:274](../../calendar_window.py#L274) `FUTURE_LEADING_MARKERS = ("향후", "앞으로")`,
  [calendar_window.py:283](../../calendar_window.py#L283) `is_future_directed_duration`).
  막는 것은 IR 이다 — [event_ir.py:301](../../event_ir.py#L301) 이
  `direction != "past"` 를 `IrSchemaError` 로 거부한다. `RelativeWindow` 에 `direction` 필드는 있는데
  값이 하나뿐이다. 귀결은 `semantic_registry_gap`(문구 없음, 케이스 F).
- **#85 `3개월 전부터 1개월 전까지 주문한 회원`** — `boundary_from` · `boundary_until` 로 분류는
  되지만([calendar_window.py:223](../../calendar_window.py#L223)) 두 경계를 한 구간으로 접는 문법이 없다.
  한쪽만 창으로 읽어 반쪽 구간을 내지 않은 것은 옳은 판단이다.

**범용 해결책.** 창을 `(anchor, direction, from_boundary, to_boundary)` 로 일반화한다.
확정 시점에 절대 구간으로 낮추는 기존 관례는 유지한다 — 방향은 그 확정에만 쓰인다.
`direction` 필드는 이미 있으므로 값 하나를 더 받는 일이고, 두 경계는 이미 분류돼 있으므로
합성 규칙 하나가 는다. 미래 창은 `BUY_DUE_DATE` 처럼 **미래를 담는 컬럼**에만 허용해야 한다
(과거 사건 컬럼에 미래 창을 걸면 항상 0건이다) — 그 허용 여부는 카탈로그 필드 선언에 싣는다.

## E. 기간 결핍 오신고

| id | 원문 | 사용자가 받은 문구 | 왜 틀렸나 |
|---|---|---|---|
| 62 | 최근 **30일**에는 구매하지 않았지만 과거 구매 이력은 있는 | 기간 값이 없습니다. | 기간이 문장에 있다 |
| 57 | **최근 3개** 캠페인 중 하나라도 구매 반응을 보인 | '최근'에 기간이 없다 | '최근'이 수식하는 것은 캠페인 **개수**이지 기간이 아니다 |

두 건의 뿌리가 다르다.

- **#62**: 창이 **부정 절**에 붙어 있어 소유자를 못 찾았다(B1 과 같은 수리). `30일`이 원문에 있으므로
  이 문구는 사실이 아니다.
- **#57**: `최근`의 머리(head)가 기간이 아니다. `최근 3개 캠페인`은 "최근 실행된 캠페인 3개"로
  확정 가능한 표현인데 맨 '최근'으로 읽혔다. 이미 저장소에 있는 원칙("최근/현재/직전의 뜻은 낱말이
  아니라 머리가 정한다")이 이 자리에 적용되지 않았다.

> **#41 은 여기에 넣지 않는다.** `최근 캠페인 발송 성공 횟수가 3회 이상이고…`의 '최근'은 정말로
> 기간이 없는 맨 표지이고, 기간을 지어내지 않고 되묻는 것이 **확정 정책**이다(fail-close).
> 코퍼스 #5 의 note 는 배포 기본 기간(`AUDIENCE_DEFAULT_PERIOD=3 day`)이 켜졌다고 적고 있으나,
> 이 배포에서는 그렇지 않다 — 실행 중인 api 컨테이너에 그 환경변수가 **없고**
> ([default_period_policy.py:59](../../default_period_policy.py#L59) 가 읽는 이름),
> 기준선의 #5 도 `clarification` 이다. 즉 #41 과 #5 는 서로 일치하며 둘 다 정책대로 동작한다.
> 정책을 켤지는 별개 결정이고, 켜면 두 항목이 함께 움직여야 한다.

**범용 해결책.** 기간 결핍을 **절 단위 스팬 정산**으로 바꾼다.

1. 어느 절이 창을 갖는지 근거 스팬으로 기록한다. 창을 가진 절이 하나라도 있으면 문장 전체의
   결핍으로 올리지 않는다. 이미 있는 원칙(`audience_issue_contract.period_issue_owned_by_lowered_clause`
   — "그 절이 실제로 컴파일되면 창은 이미 확정된 것이다")을 문장에서 절로 내린다.
2. 기본 기간 백필도 절 단위로 건다. 창이 없는 절에만 채우고, 채웠다는 사실을 의미 검증기에 고지한다
   (정책이 채운 값을 검증기가 모르면 자기 SQL 을 근거 없는 조건으로 되잡는다).
3. `최근` 같은 상대 표지는 **머리를 확정한 뒤에만** 기간으로 읽는다. 머리가 개수·순위면 기간 결핍을
   신고하지 않는다.

## F. 사유 없는 실패 — 사용자에게 할 말이 없다

| id | 귀결 | `failure_reason` | 사용자가 본 것 |

받을 곳이 없다.

**범용 해결책.**

1. **정직화 먼저.** "주체가 회원이 아닌 요청"을 인식해 `unsupported` 로 닫고, 사유와 개방 조건을

2. `semantic_registry_gap` 이 **어느 심볼이 없는지** 말하게 한다. `capability_audit` 에 이미 심볼·gap
   개념이 있고 `/health` 가 `gap_count` 를 보고한다 — 그 정보가 응답까지 오지 않을 뿐이다.
   "담당자에게 문의"만으로는 담당자도 어디를 볼지 모른다.
3. 확장은 그다음이다. `subject` 를 복수로 선언할 수 있게 하고 브랜드를 주체로 추가하면
   #44 와 #46 이 같은 선언을 공유한다.

## G. 증거 회계 퇴행 (#47)

`이메일, 문자, 앱푸시 중 정확히 두 개 채널에 동의한 회원` — 기준선 `sql`, 이번 `clarification`.
사용자가 받은 문구:

> 이 조건은 프로필 boolean 필드(subject.*)의 조합으로 **표현은 가능하지만**, 각 Comparison 에
> 필요한 정확한 evidence substring …

이 축에는 전용 계약이 있다([consent_cardinality.py](../../consent_cardinality.py) —
"정확히 N개 동의"의 진리표를 검증해 받아들인다). 표현 가능하다고 스스로 말하면서 **근거 스팬 요구**
때문에 막혔다. 형제 항목 #50(`모두 동의`)과 #56(`하나 이상 동의`)은 이번에도 SQL 이 나왔으므로
축 전체가 죽은 것이 아니라 `정확히 N` 갈래만 걸린다.

**범용 해결책.** 증거(evidence)는 **출처 추적**이지 의미 판정이 아니다.
스팬을 못 만들었다는 이유로 컴파일 가능한 요구를 막으면, 근거 회계가 능력 판정을 덮어쓴다.

1. 스팬 결손은 **경고**로 내리고 컴파일은 진행한다(귀결을 바꾸지 않는 진단).
2. 여러 필드를 한 어구가 함께 지시하는 경우(`이메일, 문자, 앱푸시 중 정확히 두 개`)는 필드마다
   따로 스팬을 요구하지 않고 **그 어구 전체를 공유 근거**로 인정한다. 카디널리티 조건은 본래
   개별 필드가 아니라 필드 **집합**에 걸리는 술어다.
3. 스팬을 강제해야 하는 자리는 "같은 어구가 두 번 해석되는 것을 막을 때"뿐이다 — 그 목적이 없는
   자리에서는 요구하지 않는다.

다만 **#73 의 사유 문구는 부정확하다**:
`이 시간 조건은 선언된 값 2개를 요구하지만 문장에서 확인된 값은 1개입니다`.
실제 이유는 "회원 상태(`MEMBER_STATE_CD`) 이력 소스가 없다"(`STATE_GRADE` 는 활동등급으로 무관)이며,

문장을 고치라고 안내하게 되는데, 문장으로는 절대 열리지 않는다.

## 4. 이 문서를 거짓이 되지 않게 하는 것

문서에 표를 두 벌 적으면 갈라진다. 아래는 **코드가 강제해야 할** 주장들이다.

| 주장 | 무엇이 강제해야 하나 |
|---|---|
| 컴파일 결과에 최상위 `OR` 이 남지 않는다 | property 테스트(임의 And/Or/Not 트리) + 러너의 출고 SQL 린트 |
| `#42` 와 `#43` 은 다른 SQL 을 낸다 | 회귀 테스트(현재 바이트 동일이므로 즉시 실패한다) |
| 컴파일되는 요구를 미지원으로 닫지 않는다 | 미지원 귀결에 대해 컴파일 시도가 성공하면 실패하는 모순 금지 테스트 |
| 모든 실패 귀결에 사용자 문장이 있다 | `clarification_questions` 가 비고 `unsupported_reason` 도 빈 응답 금지 |
| 부재 의미는 `supports_all_occurrences` 관측에만 사상된다 | 시간 카탈로그 계약 테스트 |
| 시각 조건이 SQL 에서 사라지면 성공으로 세지 않는다 | 이미 의미 검증기가 한다(#69 에서 실제로 잡았다). 유지 |

> **기준선 갱신에 관하여.** 이번 실측은 기준선 파일에 반영하지 않았다. 반영은
> `tools/update_live_prompt_baseline.py` 로 하되, **A 케이스를 고치기 전에 갱신하면
> `#55` 의 전체 회원 반환이 `sql`(성공)로 기록에 남는다.** 조용한 오답을 성공으로 굳히는 갱신은
> 하지 않는 편이 낫다.
