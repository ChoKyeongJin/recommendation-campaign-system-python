# 날짜·시각 의미 정책

시간 표현의 **문법**은 `calendar_window.py` 하나가 소유한다(이 문서는 그 문법이 어떤 뜻을
확정하는지에 대한 선언이다). 물리 컬럼과 SQL 모양은 `graph_rag._purchase_date_predicate` 계열이,
canonical 실행 IR 표현은 `event_ir.AbsoluteInterval` 이 갖는다.

`temporal_ir/` 의 정책 문서(`temporal_semantic_framework.md` 의 '시간 정책')와는 다른 계층이다.
그쪽은 **월별 스냅샷 관측**의 시간 의미이고, 여기는 **사건(주문 등)이 일어난 날짜·시각**이다.
겹치는 규칙(시간대·반개구간)은 아래와 같은 값을 쓴다.

## 확정된 정책

| 항목 | 정책 |
| --- | --- |
| 시간대 | `Asia/Seoul` |
| 내부 구간 | 반개구간 `[start, end_exclusive)` |
| 시각 토큰의 뜻 | **말한 정밀도의 단위 전체 구간** |
| 한국어 `까지` | 말한 단위의 마지막 순간까지 **포함** |
| 열린 경계 | `X까지`/`X 이전` = 시작이 열림 · `X 이후`/`X부터`/`X 이래` = 끝이 열림 |
| 주 경계 | 월요일 00:00 부터 다음 월요일 00:00 전까지 |
| `오늘` | 달력상 오늘 하루(기준일 고정) |
| `최근 24시간` | 기준 시각에서 거슬러 24시간 — **`오늘`과 다른 조건이다** (미구현) |

### 시각 토큰은 그 단위 전체다

`9시` = 09:00:00~09:59:59, `9시 30분` = 09:30:00~09:30:59, `23시 59분 59초` = 그 1초.
날짜의 `7월까지`가 7월 말일을 포함하는 것과 같은 단위 의미론이다. 그래서 `까지`가 "해당 초를
포함"한다는 규칙이 저절로 따라온다 — 별도 예외가 아니다.

반개구간 규칙과 모순되지 않는다. 초 해상도의 `CHAR` 시각 컬럼에서 `<= '185959'` 와
`< '190000'` 은 같은 집합이므로, 저장 표기가 포함 끝(`to_time`)이어도 뜻은 반개구간이다.

### 경계 낱말은 칸이 아니라 방향이다

`2026년 7월 1일 23시 59분 59초까지 주문한 회원`의 `까지`를 읽지 않으면 남는 것은 '그 1초'라는
칸뿐이고, 요청 집합의 극히 일부(거의 0건)가 나온다. 열린 쪽은 적재 범위 전체를 뜻하는 센티널
날짜(`calendar_window.OPEN_WINDOW_MIN_DATE` / `OPEN_WINDOW_MAX_DATE`)로 닫고, 방향은
`open_start` / `open_end` 표지로 함께 남긴다 — 센티널을 모르는 소비자도 '이 경계는 원문이 말한
것이 아니다'를 읽을 수 있어야 한다.

범위(`A부터 B까지`)는 접히면서 닫는 말까지 원문 구간에 삼키므로 열린 구간과 서로를 가로채지
않는다. 나열(`2월과 3월`)의 각 구간도 열리지 않는다.

### 반복 시각대는 창이 아니라 시각 조건이다

날짜 없는 시각 범위(`밤 11시부터 다음 날 새벽 2시 사이`)는 어느 하루가 아니라 **매일 되풀이되는
시각대**다. 날짜 창과 직교하므로 `purchase_date.time_of_day = {from_time, to_time}` 에 따로 싣고
날짜 조건과 AND 로 결합한다.

단독 시각(`9시 이후 주문`)은 여전히 잡지 않는다 — 그날의 시점인지 매일의 시각대인지 원문이
확정하지 않는다(fail-close).

## SQL 낮춤

물리 컬럼은 카탈로그가 소유한다(`purchase.order_time` → `ORDER_TIME`). 시각은 주문 **헤더**에만
있으므로, 상세 기반 문맥에서는 헤더 상관 `EXISTS`(ORDER_ID 조인)로 표현하고 그것도 불가능하면
술어를 **아예 만들지 않는다**(날짜만 걸면 조건이 넓어진 채 실행된다).

정확한 timestamp 경계는 날짜 비교 위에 경계일에만 시각을 얹는다 — 색인이 살아 있고, 가운데 날은
전일이 포함된다.

```sql
-- ... <= D,T
date BETWEEN <최소> AND D AND (date < D OR time <= T)
-- ... >= D,T
date BETWEEN D AND <최대> AND (date > D OR time >= T)
```

반복 시각대는 자정 횡단 여부가 AND 와 OR 를 가른다. 같은 두 경계로 정반대 오답을 만들 수 있는
자리라 판정을 `calendar_window.time_of_day_crosses_midnight` 하나가 소유한다.

```sql
-- 같은 날 범위: 09:00 ~ 18:59:59
(time >= '090000' AND time <= '185959')
-- 자정 횡단: 23:00 ~ 다음 날 02:00 전
(time >= '230000' OR time <= '015959')
```

`<= '015959'` 는 `< '020000'` 과 같은 집합이다. 표기를 포함 끝으로 통일하는 이유는 날짜 창의
`to_time` 과 한 규칙을 쓰기 위해서다.

## 조용한 드롭 금지

시각 조건이 plan 에 실렸는데 SQL 에 시각 컬럼이 없으면 출고를 막는다
(`graph_rag._verify_sql_semantic_invariants` 의 `time_window_dropped`). 검사는 슬롯 이름이 아니라
**구조**로 훑으므로 새 창 슬롯도 자동으로 대상이 된다.

원문이 반복 시각대를 말했는데 plan 어디에도 `time_of_day` 가 없으면 결정론 드롭 감지기가 이름을
대고 고지한다 — 침묵하면 '그 시간대 주문'이 '아무 때나 주문'이 된다.

canonical 실행 IR(`event_ir.AbsoluteInterval`)은 시각 경계를 **잃지 않고 나른다**
(`start_time`/`end_time`). 날짜 단위 컬럼에 바인딩된 시간 필터는 시각 경계가 걸린 구간을 받으면
근사하지 않고 `SqlCompileError` 로 닫는다 — 시각을 표현할 수 있는 경로가 따로 있고, 그쪽으로
가야 한다.

고정: `tests/test_time_of_day_semantics.py` (경계 행은 **생성된 술어를 파싱해 평가한다** — 같은
논리를 파이썬으로 다시 적으면 AND/OR 가 뒤집혀도 복사본이 함께 뒤집혀 아무것도 잡지 못한다).

## 아직 하지 않은 것

- **`최근 24시간`** 같은 시각 해상도 롤링 창. `시간`은 기간 단위 어휘가 아니라 창이 만들어지지
  않는다(맨 `최근`과 같은 자리로 귀결). 열려면 날짜+시각 두 컬럼에 걸친 롤링 컷오프가 필요하다.
- **`3개월 전부터 1개월 전까지`** — 상대 앵커 두 개로 만든 범위. 경계 종류
  (`boundary_from`/`boundary_until`)로 분류만 되고 두 경계를 한 구간으로 접는 문법이 없다.
  한쪽만 창으로 읽어 반쪽 구간을 내는 것이 최악이라 그쪽으로 열지 않았다.
- **미래 방향 창**(`향후 7일`). 지금까지의 창 문법은 전부 과거 방향이다. 미래 창을 과거 창으로
  읽으면 정반대 집합이 나오므로, 열기 전에 방향을 창 표기에 실어야 한다.
